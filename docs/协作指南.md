# Handoff Engine 使用指南——写给产品经理

> 你好，我是闫海洋。这篇指南是专门为你写的。你不需要懂 Git、不需要懂 JSON，只需要会用 Claude Code 和一个终端。

---

## 一、什么是 Handoff Engine

**Handoff Engine 是一个帮你把工作"交出去"的工具。**

在真实的项目中，PM 写完需求要交给后端，后端做完接口要交给前端，前端实现完要交给 QA 测试。每一次交接都可能丢东西——需求文档漏了一页、接口改了没人通知、测试发现某条验收条件压根没实现。

Handoff Engine 解决了这个问题。它做的事情很简单：

1. 你告诉它"我要把这份文档交给后端"——它检查契约，确保你没有遗漏关键信息
2. 接收方收到交接，知道哪些文件是必须的、哪些是可选的、哪些缺失了
3. 整个交接过程有记录，谁在什么时候交接了什么，全部可追溯

你不需要看代码。你只需要用四个命令。

## 二、快速开始——4 步完成第一次 Handoff

### 第 1 步：准备好你要交出去的东西

在你的项目目录里放好文件。比如说你写了一份 PRD 和一份数据模型草稿：

```bash
mkdir -p /tmp/my-feature
echo "# V2.1 用户权限模块 PRD" > /tmp/my-feature/需求.md
echo "# 数据库字段定义" > /tmp/my-feature/data-model.md
```

### 第 2 步：在 AgentGraph 目录下执行 handoff

```bash
cd ~/AgentGraph
./guild handoff \
  --from product-manager \
  --to backend-architect \
  --message "V2.1 用户权限模块需求交接" \
  --path /tmp/my-feature
```

你会看到类似这样的输出：

```
创建交接 #3: product-manager → backend-architect
  状态: incomplete
  完整度: 1/3 项已提供
  [!!] 缺失 2 项:
       - 带有清晰数据模型含义（实体、关系、基数、生命周期）的产品需求。预期流量模式（峰值 RPS、数据量、增长率）。
       - 在实现开始前，对所提议的端点设计和响应形状提供 API 可用性反馈。
  记录: ~/AgentGraph/handoffs/2026-07-23-product-manager-to-backend-architect.json
```

看到"缺失 2 项"了吗？别慌，这不是报错——这是 Handoff Engine 在帮你检查契约，告诉你后端还需要补充什么信息。

### 第 3 步：检查交接状态

```bash
./guild check --handoff 3
```

输出：

```
交接 #3: product-manager → backend-architect
状态: incomplete
时间: 2026-07-23T19:45:39+08:00
完整度: 1/3 项
缺失项:
  - 带有清晰数据模型含义（实体、关系、基数、生命周期）的产品需求。预期流量模式（峰值 RPS、数据量、增长率）。
  - 在实现开始前，对所提议的端点设计和响应形状提供 API 可用性反馈。
```

### 第 4 步：接收方确认

后端看到交接后，运行以下命令表示"我收到了，我开始干活"：

```bash
./guild accept --handoff 3 --as backend-architect
```

输出：

```
接收交接 #3 ...
交接 #3 已接收 — backend-architect 开始工作
```

完成。以上四步就是一次完整的 Handoff。

## 三、四个命令详解

### 1. `guild handoff`——创建交接

**用途**：当你完成了一份工作，需要交给下一个角色时使用。

**参数**：

| 参数 | 说明 | 示例 |
|------|------|------|
| `--from` | 你的角色 | `product-manager` |
| `--to` | 接收方角色 | `backend-architect` |
| `--message` | 交接说明 | `"V2.1 用户权限模块需求"` |
| `--path` | 你准备好的文件目录 | `/tmp/my-feature` |

**示例**：

```bash
./guild handoff \
  --from ui-designer \
  --to frontend-engineer \
  --message "首页改版设计稿" \
  --path /tmp/homepage-redesign
```

**注意**：`--from` 和 `--to` 的角色名必须跟 `contracts/guild-contracts.yml` 中定义的一致。不记得有哪些角色？运行 `./guild list` 查看所有可用角色和契约。

### 2. `guild check`——检查交接完整性

**用途**：查看某一次交接是否完整，哪些东西已经提供了，哪些还缺着。

**参数**：

| 参数 | 说明 | 示例 |
|------|------|------|
| `--handoff` | 交接编号（从 handoff 输出的 # 号看） | `3` |

**示例**：

```bash
./guild check --handoff 3
```

输出会告诉你：这次交接涉及几项必须提供的资料，其中哪些已经到位，哪些还缺失。

### 3. `guild status`——查看所有交接状态

**用途**：不用记编号，看一眼就知道当前所有的交接情况。

**示例**：

```bash
./guild status
```

输出：

```
当前交接状态:

  ✔️ #2: product-manager → backend-architect (accepted) — 2026-07-23T19:44:32
  ⚠️ #3: product-manager → backend-architect (incomplete) — 2026-07-23T19:45:39
```

图标含义：
- `✔️` 已接收——接收方确认收到
- `⚠️` 不完整——还有资料缺失
- `🔄` 待处理——创建成功，等待接收方确认

### 4. `guild accept`——接收交接

**用途**：你是接收方，确认收到了交接，开始你的工作。

**参数**：

| 参数 | 说明 | 示例 |
|------|------|------|
| `--handoff` | 交接编号 | `3` |
| `--as` | 你的角色名 | `backend-architect` |

**示例**：

```bash
./guild accept --handoff 3 --as backend-architect
```

**注意**：只有 `--to` 指定的角色才能接收。如果你是 PM，交接给了后端，前端试图接收会报错。

## 四、交接契约是如何工作的

每次你执行 `handoff` 时，它都会自动检查一份叫 **契约** 的文件。这份文件位于：

```
contracts/guild-contracts.yml
```

它是在 AgentGraph 初始化时自动生成的，定义了每个角色**应该交付什么**、**需要从谁那里接收什么**。

举个例子，契约中规定：

- **产品经理**交付给**后端架构师**时，必须提供：清晰的数据模型含义（实体、关系、基数、生命周期）、预期流量模式等
- **后端架构师**交付给**前端工程师**时，必须提供：API 合同（完整请求/响应结构和错误码）、数据库模式、认证授权流程等

你可以把它想象成一份"团队对账表"——每个角色都写好了"我需要什么才能开工"，别人交过来的时候自动核对，缺了立刻告诉你。

**你不需要看代码，不需要修改这个文件。** 如果项目中的角色分工变了，操作手册里会告诉你怎么更新契约。平时使用，你只需要知道有这么个东西在背后帮你检查就够了。

## 五、常见问题

### "为什么显示缺失？"

Handoff Engine 检查的是"你提供的文件里是否包含了契约要求的信息"。比如契约要求"数据模型定义"，但你只给了一个 PRD 文档，里面没有写数据库字段——它就会标记为缺失。

这不是报错，这是一个提示：**提醒你还有信息需要补充**，这样后端就不会因为信息不全而返工。你可以这样理解：缺失提醒是你的保护伞。

### "怎么补充缺失项？"

很简单。把你缺少的资料补到文件目录里，然后重新执行 handoff 命令，路径指向同一个目录：

```bash
./guild handoff \
  --from product-manager \
  --to backend-architect \
  --message "V2.1 用户权限模块需求（已补充数据模型）" \
  --path /tmp/my-feature
```

如果新的文件匹配了缺失项，完整度就会提升。

### "交接记录在哪里？"

所有交接记录都保存在 `handoffs/` 目录下，每个交接一个 JSON 文件，文件名带日期和角色名，方便查找：

```
handoffs/
  2026-07-23-product-manager-to-backend-architect.json
```

你可以用任何文本编辑器打开查看。如果不需要了，直接删除文件即可。

### "./guild 说 --from is required，怎么回事？"

说明你执行 `handoff` 时忘记加参数了。Handoff Engine 的每个命令都有必要的参数——忘记加就会提示。按上面的表格补上就行。

### "执行时显示 command not found"

确保你在 AgentGraph 目录下运行：

```bash
cd ~/AgentGraph
```

然后再执行 `./guild` 开头的命令。或者把这个目录加到你的 PATH 里，就可以在任何地方直接打 `guild` 了。

## 六、进阶技巧

### 链式交接：PM → 后端 → 前端 → QA

一个功能从立项到上线通常要经过多轮交接。你可以这样做：

```bash
# 第 1 轮：PM 交给后端
./guild handoff --from product-manager --to backend-architect \
  --message "V2.1 需求" --path /tmp/v2.1-prd

# 第 2 轮：后端完成后交给前端
./guild handoff --from backend-architect --to frontend-engineer \
  --message "API 就绪" --path /tmp/v2.1-api

# 第 3 轮：前端完成后交给 QA
./guild handoff --from frontend-engineer --to qa-engineer \
  --message "功能完成，可测试" --path /tmp/v2.1-build
```

每一轮交接都会独立记录，契约会检查对应角色的交付要求。你不必记住所有契约细节——Handoff Engine 每次都会帮你自动核对。

### 同时传给多人

如果你的工作需要同时交给两个角色（比如设计稿同时交给前端和 QA），分别执行两次 handoff 即可：

```bash
./guild handoff --from ui-designer --to frontend-engineer \
  --message "首页设计稿" --path /tmp/designs

./guild handoff --from ui-designer --to qa-engineer \
  --message "首页设计稿（供测试参考）" --path /tmp/designs
```

两次交接各自独立，契约检查的内容也不一样——前端会检查组件状态覆盖，QA 会检查验收条件。

### 交接编号快速参考

执行 `./guild status` 可以看到所有交接的编号和状态。如果你有一堆交接，用 status 看一眼就知道哪些还没完成、哪些已经接收了。
