# AgentGuild 流水线指南

## 1. 什么是流水线

流水线（Pipeline）是 AgentGuild 的核心编排机制，它将多个阶段的 Agent 协作串成一条线。

在实际项目中，一个完整的产品开发流程往往涉及多个角色依次接力：产品经理定义需求、设计师设计界面、工程师实现功能、QA 验证质量。每次角色切换都是一次「交接」（Handoff），而流水线就是把这些交接自动串联起来。

**流水线的核心价值：**
- 标准化：每个阶段的输入输出明确，减少沟通成本
- 自动化：阶段间的交接自动触发，无需手动逐个创建
- 可追溯：每个交接都有完整记录，随时可以回溯
- 可复用：一套流水线定义可以在多个项目中重复使用

## 2. 怎么运行

运行一条流水线使用 `guild run` 命令，需要指定流水线名称和工作目录：

```bash
guild run --pipeline startup-mvp --path ./my-project/
```

### 参数说明

| 参数 | 必填 | 说明 |
|------|------|------|
| `--pipeline <name>` | 是 | 流水线名称，对应 `pipelines/` 目录下的 YAML 文件名（不含 .yml） |
| `--path <dir>` | 是 | 项目工作目录，交付物和产出文件存放在此 |
| `--dry-run` | 否 | 模拟运行，不创建实际交接记录，只展示流程 |
| `--list` | 否 | 列出所有可用的流水线 |

### 运行流程

1. 执行阶段 1 → 阶段 2 的交接：
   - 显示当前阶段和下一阶段的 Agent 列表
   - 提示你在 `--path` 目录中准备交付物
   - 按 Enter 确认继续，或输入 `skip` 跳过
   - 自动为每对（当前 Agent → 下一阶段 Agent）创建交接记录
   - 检查交付物完整性，缺失项会警告
2. 阶段 2 → 阶段 3，重复上述流程
3. 直至所有阶段完成

### 示例

```bash
# 列出可用流水线
guild run --list

# 模拟运行功能开发流水线
guild run --pipeline feature-dev --path /tmp/my-feature --dry-run

# 实际运行 MVP 开发流水线
guild run --pipeline startup-mvp --path ./my-startup/
```

## 3. 查看可用流水线

使用 `--list` 参数可以查看所有已注册的流水线：

```bash
guild run --list
```

输出示例：

```
  startup-mvp — 创业 MVP 开发
    从零到 MVP 的完整产品开发流水线（发现 → 设计 → 实现 → 验证）
  feature-dev — 功能开发
    单个功能的开发流水线（需求 → 设计 → 实现 → 审查）
```

流水线文件存放在 `pipelines/` 目录下，每个 `.yml` 文件对应一条流水线。

## 4. 流水线文件格式

流水线使用 YAML 格式定义，结构如下：

```yaml
name: 流水线名称          # 必填，显示用中文名称
description: 描述文字      # 选填，说明流水线的用途和适用场景
phases:                   # 必填，阶段列表（至少 2 个阶段）
  - phase: 阶段名称        # 必填，当前阶段的名称
    agents:               # 必填，参与该阶段的 Agent 列表
      - agent-slug
      - another-agent
    delivers:             # 选填，该阶段产出的交付物列表
      - 交付物1
      - 交付物2
    requires_from: 上一阶段 # 选填，说明从哪个阶段接收输入
```

### 字段说明

- **name**: 流水线的人类可读名称，在 `--list` 中显示
- **description**: 流水线的简短描述，帮助用户理解使用场景
- **phases**: 一个有序的阶段数组，按执行顺序排列
  - **phase**: 阶段的名称
  - **agents**: 参与该阶段的 Agent slug 列表，需在 `guild.config.json` 中注册
  - **delivers**: 该阶段产出的交付物清单，用于交接时检查完整性
  - **requires_from**: 说明该阶段的输入来自哪个阶段（参考信息，流水线自动按顺序传递）

### 关键规则

- 流水线必须包含至少 2 个阶段
- 每个阶段至少需要 1 个 Agent
- Agent slug 必须在 `guild.config.json` 中有对应注册
- 流水线文件必须以 `.yml` 为扩展名

## 5. 两个预置流水线

### startup-mvp.yml — 创业 MVP 开发

适用于从零开始的产品开发，覆盖完整的产品研发周期：

1. **发现与定义**（product-manager, ux-researcher）
   - 产出：问题陈述、用户洞察、产品需求文档
2. **设计**（ui-designer, interaction-designer）
   - 产出：设计规范、交互规范、视觉稿
3. **工程实现**（frontend-engineer, backend-architect, devops-engineer）
   - 产出：可运行构建、API 规范、部署流水线
4. **质量验证**（qa-engineer, creative-director）
   - 产出：质量报告、设计评审、发布决策

**适合场景：** 新产品立项、从 0 到 1 的项目、黑客马拉松

### feature-dev.yml — 功能开发

适用于在现有产品上开发单个功能，更轻量和聚焦：

1. **需求定义**（product-manager）
   - 产出：PRD、用户故事、验收条件
2. **设计**（ui-designer）
   - 产出：UI 设计稿、交互说明
3. **实现**（frontend-engineer, backend-architect）
   - 产出：功能代码、API、测试
4. **审查**（tech-writer, creative-director）
   - 产出：文档更新、设计审查、发布就绪

**适合场景：** 已有产品的功能迭代、Bug 修复、小版本发布

## 6. 怎么自定义

自定义流水线非常简单，只需复制一个已有的 YAML 文件并根据需要修改。

### 步骤

1. 复制一个现有流水线作为模板：

```bash
cp pipelines/feature-dev.yml pipelines/my-pipeline.yml
```

2. 编辑 `my-pipeline.yml`，根据你的需求修改：

```yaml
name: 我的自定义流水线
description: 适用于 XXX 场景
phases:
  - phase: 第一阶段
    agents: [agent-a]
    delivers: [产出物A]
  - phase: 第二阶段
    agents: [agent-b, agent-c]
    delivers: [产出物B, 产出物C]
  # 继续添加更多阶段...
```

3. 运行你的自定义流水线：

```bash
guild run --pipeline my-pipeline --path ./project/
```

### 最佳实践

- **阶段数量建议 2~5 个**，太少失去编排价值，太多增加等待成本
- **每个阶段的 Agent 数量适中**（1~3 个），太多 Agent 之间的交接矩阵会爆炸
- **交付物描述尽量精确**，便于交接时的完整性检查
- **先 dry-run 验证**，确认流程符合预期后再实际运行：
  ```bash
  guild run --pipeline my-pipeline --path ./project/ --dry-run
  ```
