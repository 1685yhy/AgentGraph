# 迭代指南：从 0→1 到 1→N

## 为什么构建只是开始

AgentGraph 的核心能力是**用多 Agent 协作把东西造出来**——这是 0→1 的能力。

但真正的产品生命周期不是"造完就结束"。Color Clash 游戏通过 40 个 Agent + 4 层协作机制完成了开发，却带着一个"开始按钮触发分享弹窗"的 bug 发布了。

原因很清楚：**我们有构建流水线，但没有迭代流水线。**

0→1 回答"能不能做出来"，1→N 回答"能不能做对、做好、持续改进"。

## 完整生命周期

```
handoff → verify → accept → feedback → fix → verify → accept → changelog
```

### 1. Handoff（交接）

```bash
guild handoff --from game-programmer --to game-qa-engineer --path ./deliverables
```

创建交接记录，自动检查交付物是否满足契约要求。

### 2. Verify（质量验证）

交接创建时**自动运行**。也支持单独调用：

```bash
guild verify --type html --file demos/color-clash.html
guild verify --path ./deliverables
guild verify --handoff 5
```

按文件类型执行不同检查：

| 类型 | 检查项 |
|------|--------|
| HTML | `<script>` 闭合标签、viewport meta、DOM 结构、事件绑定 |
| Markdown | frontmatter 完整性、本地链接有效性 |
| Bash | `bash -n` 语法检查、不安全模式检测 |
| JSON | JSON 解析、必需字段 |
| CSS | 大括号匹配 |
| JS/TS | Node.js 语法检查 |
| 通用 | 文件非空、UTF-8 编码、无 BOM 头 |

### 3. Accept（接收）

```bash
guild accept --handoff 5 --as game-qa-engineer
```

接收时自动检查三道质量门禁：

1. **完整性门禁**：所有必需项已提供？（status 必须为 ready）
2. **验证门禁**：所有文件通过质量检查？
3. **反馈门禁**：没有关联的未解决 critical bug？

任一检查不通过则拒绝接收，并给出具体原因。

```
$ guild accept --handoff 5 --as game-qa-engineer
  ❌ 无法接收:
      - 质量验证未通过: color-clash.html (JS运行时错误风险)
      - 关联的未解决 bug: fb-001 (开始按钮触发分享弹窗)
  → 请修复后重新 handoff
```

### 4. Feedback（反馈）

发现 bug 或改进点时记录反馈：

```bash
# 记录 bug
guild feedback --handoff 3 --type bug --severity critical \
  --summary "开始按钮显示分享弹窗而非开始游戏" \
  --repro "打开页面 → 点击开始试炼 → 看到分享弹窗"

# 记录改进
guild feedback --handoff 3 --type improvement \
  --summary "增加音效开关"

# 列出反馈
guild feedback --list
guild feedback --list --status open
guild feedback --list --handoff 3

# 链接修复
guild feedback --fix fb-001 --handoff 6
```

### 5. Fix → Verify → Accept（修复闭环）

创建修复 handoff → 自动验证 → 接收 → 链接反馈：

```bash
# 1. 创建修复交接
guild handoff --from game-programmer --to game-qa-engineer \
  --path /tmp/colorclash --message "修复 fb-001 后重新交付"

# 2. 如果验证通过，接收
guild accept --handoff 6 --as game-qa-engineer

# 3. 链接回原始反馈
guild feedback --fix fb-001 --handoff 6
```

### 6. Changelog（变更日志）

```bash
guild changelog
```

输出示例：

```
v0.2.0 (2026-07-24)
------------------------------
  ✅ 修复: fb-001: 开始按钮触发分享弹窗
     [handoff #6]

v0.1.0 (2026-07-23)
------------------------------
  ✅ product-manager → backend-architect: 初始交付 [handoff #1]
```

## 反馈文件格式

存储在 `context/feedback/<id>.json`：

```json
{
  "id": "fb-001",
  "handoff_id": 3,
  "type": "bug",
  "severity": "critical",
  "summary": "开始按钮触发分享弹窗",
  "repro_steps": "1.打开页面 2.点击开始试炼 3.看到分享弹窗",
  "status": "open",
  "linked_fix_handoff": 6,
  "created": "2026-07-24T12:00:00Z",
  "resolved": "2026-07-24T14:00:00Z"
}
```

## 最佳实践

1. **交接即验证**：每次 handoff 都会自动验证交付物质量，不需要手动触发
2. **先修 Bug 再新功能**：accepted 之前确保没有 critical bug
3. **反馈即文档**：每个反馈都是团队的集体记忆，减少重复犯错
4. **Changelog 自动生成**：不需要手动维护发布日志
5. **Iterate 流水线**：对于持续迭代场景，使用 `guild run --pipeline iterate`
