# 决策系统指南

## 什么是决策系统？

决策系统是 AgentGuild 的**结构化决策记录机制**，基于 **ADR（Architecture Decision Record）** 模式。每次关键决策都以 JSON 文件形式记录在 `context/decisions/` 目录下，由索引文件 `context/index.json` 统一管理。

### 核心理念

- **先决策，后实施**：在实现代码或交付物之前，先记录架构和数据设计决策。
- **预防优于修复**：记录决策时会自动进行影响分析，识别哪些 Agent 会受到此决策影响。
- **可追溯**：决策与交接记录（handoff）关联，使每个交付物都能追溯到其背后的决策依据。
- **冲突检测**：自动发现多个 Agent 对同一主题做出冲突决策的情况。

## 目录结构

```
context/
├── index.json          # 决策索引（版本、所有决策列表、冲突记录）
└── decisions/          # 单个决策记录文件
    ├── 1700000000-backend-architect-api-format.json
    ├── 1700000001-frontend-engineer-api-format.json
    └── ...
```

## 如何记录决策

### 基本命令

```bash
guild decide --agent <agent> --type <type> --topic <topic> --summary <summary>
```

### 完整参数

| 参数 | 必需 | 说明 |
|------|------|------|
| `--agent` | 是 | 决策者名称或 slug，如 `backend-architect`、`pm` |
| `--type` | 是 | 决策类型（见下方类型参考） |
| `--topic` | 是 | 决策主题，简短扼要 |
| `--summary` | 是 | 决策摘要，一两句话说明决策内容 |
| `--rationale` | 否 | 决策理由/背景 |
| `--constraints` | 否 | 约束条件或注意事项 |
| `--authority` | 否 | 决策权威方，默认取 agent 名称 |

### 示例

```bash
# 记录后端 API 格式决策
guild decide --agent backend-architect --type api-design \
  --topic "教师数据API响应格式" \
  --summary "统一使用 {code: 0, data: {...}, message: ''} 包裹响应" \
  --rationale "前端和移动端都需要统一的错误处理模式" \
  --constraints "不兼容 v1 API"

# 记录数据模型变更
guild decide --agent data-engineer --type data-model \
  --topic "用户表增加 tenant_id 字段" \
  --summary "多租户场景需要在所有业务表增加租户隔离字段" \
  --rationale "当前设计不支持 SaaS 多租户部署"
```

### 影响分析流程

执行 `guild decide` 时，系统会自动：

1. 解析代理名称
2. 读取 `contracts/guild-contracts.yml` 中的依赖关系
3. 找出依赖于该决策 Agent 的下游 Agent
4. 列出所有受影响方
5. 询问是否继续记录（可取消）

这种 **PREVENTIVE（预防性）** 检查确保在记录决策之前，决策者意识到自己的选择会影响哪些人。

## 决策类型参考

| 类型 | 使用场景 | 示例 |
|------|----------|------|
| `api-design` | API 接口设计、请求/响应格式 | 统一响应体结构、分页方案 |
| `data-model` | 数据模型、数据库表结构 | 字段命名、索引策略、关联方式 |
| `naming` | 命名规范和约定 | 变量命名风格、文件命名规则 |
| `scope` | 项目/功能范围界定 | 本期做/不做什么、MVP 边界 |
| `architecture` | 系统架构、模块划分 | 微服务拆分、通信方式、部署拓扑 |
| `deployment` | 部署策略和环境 | CI/CD 流程、环境配置、灰度发布 |
| `ux` | 用户体验和交互设计 | 导航结构、操作流程、反馈机制 |
| `brand` | 品牌风格和视觉设计 | 配色方案、字体选择、Logo 风格 |

## 决策与交接的关联

当执行 `guild handoff` 创建交接时，系统会自动检查**当前交接的发送方和接收方是否有相关决策**：

```bash
# 示例：pm 向 backend 交接
guild handoff --from pm --to backend --path /tmp/deliverables

# 输出示例：
#   上下文检查...
#     📋 相关决策: #1700000001 [pm] 教师数据API响应格式
#     → 建议确认交付物是否遵循以上决策
```

这确保接收方知道自己需要遵循哪些既有决策。

## 检查和解决冲突

### 查看决策图谱

```bash
guild context show
```

输出按类型分组显示所有决策：
```
=== 决策图谱 ===

按类型分组：
  api-design (2 条)
    #1700000000 [backend-architect] 教师数据API响应格式 (active)
    #1700000001 [frontend-engineer] 教师数据API响应格式 (active)
  data-model (1 条)
    #1700000002 [data-engineer] 用户表增加 tenant_id (active)
```

### 检测冲突

```bash
guild context check
```

执行两项检查：

1. **同主题多决策冲突**：检测同一主题上是否有多个 Agent 做出了不同决策
2. **决策追溯**：统计已有决策数量和已关联交接的交付物数量

输出示例：
```
=== 冲突检查 ===

1. 同主题多决策：
  ⚠️  冲突: 教师数据API响应格式
      #1700000000 [backend-architect]: 教师数据API响应格式
      #1700000001 [frontend-engineer]: 教师数据API响应格式

2. 决策追溯：
  总决策数: 2
  已追溯的交付物: 0

  ⚠️  发现潜在冲突，运行 guild resolve 处理。
```

### 解决冲突

当发现冲突时，需要由 PM 或架构师进行协调，流程通常是：

1. 相关方开会讨论冲突
2. 达成共识后，由权威方记录新的决策（标记旧决策为 `superseded`）
3. 或在某个决策 JSON 文件中手工设置 `"status": "superseded"` 和 `"superseded_by": <新决策ID>`

未来版本将支持 `guild resolve` 命令进行自动化冲突仲裁。

## 最佳实践

### 1. 决策先于实现

在编写任何代码之前，先使用 `guild decide` 记录关键决策。这确保：
- 团队成员了解设计方向
- 决策理由可追溯
- 减少实现后的返工

### 2. 决策粒度适中

- **不要太细**：不需要为每个变量命名都做决策
- **不要太粗**：架构级变更需要有决策记录
- **建议标准**：会影响两个以上 Agent 协作的，或会对未来产生长期影响的选择

### 3. 关联交接

记录决策后，确保后续的 `guild handoff` 中包含相关的决策引用。系统会自动匹配，但如果有特殊的决策关联需求，可以在 handoff 的 message 中说明。

### 4. 定期检查冲突

建议每隔一段时间运行 `guild context check` 来检查是否存在未发现的冲突。尤其是在以下节点：

- 新 Agent 加入项目后
- 跨团队协作关键节点
- 架构评审前

### 5. 更新决策状态

决策记录是活的文档。当决策被推翻或更新时：

1. 在新决策文件中更新 `"status": "active"`（默认）
2. 在旧决策文件中设置 `"status": "superseded"` 和 `"superseded_by": <新ID>`
3. 不要删除旧的决策文件——它们构成了项目的设计历史

### 6. 记录"不做"的决策

有时候，决定**不做什么**比决定做什么更重要。`scope` 类型的决策非常适合记录这类选择。

## 决策记录文件格式

```json
{
  "id": 1701670400,
  "agent": "backend-architect",
  "timestamp": "2025-12-04T06:40:00Z",
  "decision": {
    "type": "api-design",
    "topic": "教师数据API响应格式",
    "summary": "统一使用 {code: 0, data: {...}, message: ''} 包裹响应",
    "rationale": "前端和移动端都需要统一的错误处理模式",
    "constraints": "不兼容 v1 API",
    "authority": "backend-architect"
  },
  "impact": {
    "affects": ["frontend-engineer", "mobile-developer"],
    "breaking_changes": [],
    "notified": [],
    "confirmed": []
  },
  "traceability": [],
  "status": "active",
  "superseded_by": null
}
```

### 字段说明

| 字段 | 说明 |
|------|------|
| `id` | Unix 时间戳，唯一标识 |
| `agent` | 决策者 slug |
| `timestamp` | ISO 8601 时间戳 |
| `decision.*` | 决策内容：类型、主题、摘要、理由、约束、权威方 |
| `impact.affects` | 受影响的 Agent 列表 |
| `impact.breaking_changes` | 破坏性变更列表（预留字段） |
| `impact.notified` | 已通知方列表（预留字段） |
| `impact.confirmed` | 已确认方列表（预留字段） |
| `traceability` | 关联的 handoff 列表（预留字段） |
| `status` | `active` 或 `superseded` |
| `superseded_by` | 被哪个决策替代（`null` 或 ID 数字） |

## 流水线中的上下文检查

当使用 `guild run` 执行流水线时，每个阶段完成后会自动运行 `guild context check`，输出前 10 行结果。这确保流水线执行中能及时发现决策冲突。
